# Rule: Aggregates

## Default
Unless explicitly overridden by the project specification:

- **What:** An aggregate is a root entity plus the records that belong to it. The specification declares the root, its owned children and its dependent records (section "Aggregates" in `docs/domain/entities.md`). Today the work order is the root, its lines are owned children, payments and status history are dependent records.
- **When:** For every entity the specification declares an aggregate root.
- **Where:** All parts live in the root's feature package (`workorder`).
    - Owned child (order line): a domain record nested in the root record and a package-private JPA entity in `repository.jpa`. No port, no service, no web package of its own.
    - Dependent record (payment, status history): a domain record in the feature root, its own port in `repository/` and adapter in `repository/jpa/`. No service and no web package of its own. It refers to the root by id.
- **How (domain):**
    - The root and its children are records with `@Builder(toBuilder = true)`. A change builds a new root with a new `lines` list (copied with `List.copyOf` in the compact constructor).
    - Derived values are methods of the record, never components and never columns: `line.total()` is `quantity × price`, `order.total()` is the sum of the line totals. The balance (total minus payments) is computed in the service from the payments port.
    - Ids of children are generated by the service, including children created in the same operation (see the Entity Identifiers rule).
    - A line may be added, changed or removed only while `status.linesEditable()` is true (see the Status Transitions rule). The service checks it before it builds the new root.
- **How (persistence):**
    - The root entity maps its children with a unidirectional `@OneToMany(cascade = ALL, orphanRemoval = true)`, `@JoinColumn(name = "<root>_id", nullable = false, updatable = false)` and `@BatchSize(size = 50)`. The field has `@Setter(AccessLevel.NONE)` and `@Builder.Default` with an `ArrayList`.
    - A child entity has an assigned id and its own `@Version` (technical), so cascade persists it instead of merging it.
    - The collection is never replaced. The persistence mapper's `updateEntity` ignores `lines`, and a `default` method in the same mapper changes the existing list in place by id: remove the missing ones, update the matching ones, add the new ones.
    - Every command raises the root's version by exactly one, even when only a child changed. The Spring Data repository has a finder with `@Lock(LockModeType.OPTIMISTIC_FORCE_INCREMENT)`, and the adapter's `update` loads the root through it. The domain record the adapter returns carries the new version.
- **How (commands):** The root has no single `PUT`. There is one operation per screen section. Each has its own request type, its own rights check and carries the expected `version`. Each returns the full order with the new `version` (a delete returns the order too, not 204).
    - `PUT /{id}/info` (problem description, mileage), `PUT /{id}/diagnostic-notes`, `PUT /{id}/mechanic`.
    - `POST /{id}/lines`, `PUT /{id}/lines/{lineId}`, `DELETE /{id}/lines/{lineId}`.
    - `POST /{id}/payments`, `POST /{id}/transitions` (see the Status Transitions rule).
    - Reads: `GET /{id}` (order with lines and transitions; for a cancelled order also `cancellation`: the reason, the user and the time, taken from the history record that cancelled it), `GET /{id}/payments`, `GET /{id}/history`. The payments and the history of one order are small and are returned without pagination.
- **How (service):** One method per command, `@Transactional`. Load the root (not found if it is missing or not visible to the user) → compare `expectedVersion` with the loaded version (`ConcurrentUpdateException` on a mismatch, nothing is written) → check the rights through `CurrentUser` → check the status rules → build the new root → `update` → write dependent records through their ports in the same transaction → log. `expectedVersion` is a separate parameter next to the id.
- **Lists:** A list row carries the order total. The adapter loads the lines in batches (`@BatchSize`) and never with a fetch join of the collection in a paged query.

Example (mapper, in-place synchronization):

```java
@Mapping(target = "version", ignore = true)
@Mapping(target = "lines", ignore = true)
void updateEntity(WorkOrder order, @MappingTarget WorkOrderJpaEntity entity);

default void syncLines(List<WorkOrderLine> source, List<WorkOrderLineJpaEntity> target) {
    var ids = source.stream().map(WorkOrderLine::id).collect(Collectors.toSet());
    target.removeIf(entity -> !ids.contains(entity.getId()));
    var existing = target.stream().collect(Collectors.toMap(WorkOrderLineJpaEntity::getId, Function.identity()));
    for (var line : source) {
        var entity = existing.get(line.id());
        if (Objects.isNull(entity)) {
            target.add(toLineEntity(line));
        } else {
            updateLineEntity(line, entity);
        }
    }
}
```

Example (repository finder):

```java
@Lock(LockModeType.OPTIMISTIC_FORCE_INCREMENT)
@Query("select o from WorkOrderJpaEntity o where o.id = :id")
Optional<WorkOrderJpaEntity> findForUpdateById(UUID id);
```

## Why
- The root's version protects the whole aggregate. If only a child changed and the root's version stayed the same, a stale page would silently overwrite the change.
- Changing the list in place keeps orphan removal working. Replacing the managed collection makes Hibernate throw.
- Payments and status history are append-only facts. Outside the editable object nothing can edit them by accident, and the order does not drag a growing list.
- A computed total cannot disagree with the lines.
- One command per section turns each rights rule into one check: a mechanic may change the diagnostic notes but not the problem description.

## Exceptions
The specification may declare another shape of aggregate or ask for a stored derived value. Follow it.

## Prohibitions
- No port, service, controller or Spring Data repository for an owned child.
- No child entity outside `repository.jpa`.
- No stored total or other derived column, and no `total` component in the domain record.
- No `setLines(...)` and no other replacement of the managed collection.
- No update or delete of a dependent record, and no cascade from the root to dependent records.
- No fetch join of a collection in a paged query.
- No change of a child outside the root's commands.
- No `version` taken from a request except as the expected version.

## Special Cases
- A command that only adds a dependent record (a payment, a status change) still raises the root's version, because it goes through the root's command.
- The Update flow of the Services rule is for standalone entities. A root has commands.

## Infrastructure
- Hibernate `@BatchSize`; Spring Data `@Lock` and `@Query`.
- `ConcurrentUpdateException` in `common/exception` (`CONFLICT`, `error.concurrent-update`).

## Verification
- ArchUnit: child entities are used only in `..repository.jpa..`; there is no port or service for an owned child; the domain record of a root has no `total` component; a dependent-record port has no `update` and no `delete`.
- Integration tests (Testcontainers):
    - a root with lines is saved and loaded back unchanged;
    - removing a line deletes its row;
    - changing only a line raises the root's version by exactly one, and the returned version equals the stored one; the same when root fields change too;
    - a stale `expectedVersion` returns 409 with `error.concurrent-update`;
    - listing orders runs a bounded number of statements that does not grow with the number of orders.
- Unit tests: a stale version throws and nothing is written; a line command in a read-only status throws.
- If the version test fails, fix the mechanism, not the test.
